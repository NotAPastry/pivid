1 Introduction
The LR2021 is an advanced ultra-low power transceiver designed to operate across both Sub-GHz and 2.4GHz frequency bands,
supporting a variety of modulation schemes including LoRa®, (G)FSK, 4-FSK, FLRC, BPSK, OOK, OQPSK and LR-FHSS. This versatility
allows LR2021 to support a variety of wireless protocols, running in host Microcontroller, in addition to LoRaWAN: Bluetooth® Low
Energy, WI-SUN, WM-BUS, 802.15.4 and Z-Wave.
First-generation LoRa transceivers relied on direct register access. Similar to LoRa generation 2 and generation 3 devices
(SX1261/62/LLCC68 and LR11xx series), the LR2021 is controlled through a comprehensive API (Application Programming Interface)
based on SPI commands that simplify integration and provide a more intuitive programming model.

1.1 Purpose
This application note provides detailed instructions on how to use the LR2021 Commands for transmitting and receiving different
packet types with their corresponding modulations:

2 SPI Communication Basics
Before diving into specific modulation types, let's understand the general command sequence for transmitting and receiving packets
using the LR2021. Refer to “Host Interface” section of the LR2021 datasheet for more details.
The LR2021 is controlled via a Serial Peripheral Interface (SPI) interface operating in slave mode with a maximum frequency of
16MHz. Communication with the device follows these principles:
•

The BUSY signal is used to indicate when the device is ready for commands

•

Each command starts with a 16-bit opcode followed by required arguments

•

The device returns status information (Stat) and IRQ status with each response

2.1 SPI Write Commands
SPI write commands are fundamental operations for controlling or configuring the LR2021 transceiver.
To ensure valid operations, adhere to the following procedures:
•

Wait for the BUSY signal to be low before sending a command

•

After sending a command, read the status register (Stat) from the first bytes of the response to ensure the previous
command was processed successfully

•

Use IRQs for event notifications

2.2 SPI Read Commands
In the LR2021, an SPI read command is a sequence where the host controller requests data from the LR2021 transceiver through the
SPI bus. Unlike write commands which only send data to the device, read commands involve three steps: first sending a request,
waiting, and then receiving the response data.
As detailed in Section 5.4.1.2 of the datasheet, a read command follows this sequence:
•

•

First SPI Frame (Request):

1.

The host sends the 16-bit opcode (command identifier) and any required arguments.

2.

The LR2021 asserts the BUSY pin to indicate it's processing the command.

3.

The LR2021 returns status information (Stat) and IRQ status on the MISO line.

Wait Period:

1.
•

The host waits for BUSY to go low, indicating the data is ready.

Second SPI Frame (Response):

1.

The host initiates another SPI transaction by pulling NSS low.

2.

The host sends zeros or dummy bytes on MOSI.

3.

The LR2021 returns status information again, followed by the requested data.

The LR2021's read commands allow you to retrieve various types of information:
•

•

•

Device Status Information:
o Current chip operating mode (GetStatus(...)),
o Firmware version information (GetVersion(...)),
o Error flags and conditions (GetErrors(...))
Measurements and Sensor Data:
o Battery voltage measurement (GetVbat(...)),
o Temperature measurement (GetTemp(...)),
o Instantaneous received signal strength (GetRssiInst(...)),
o Timing information for events (GetTimestampValue(...))
FIFO and Packet Data:
o Length of the last received packet (GetRxPktLength(...)),
o Current fill level of the RX FIFO (GetRxFifoLevel(...)),
o Current fill level of the TX FIFO (GetTxFifoLevel(...))

Note: Reading received data from RX FIFO uses the Direct Read command (see Section 2.3.2) rather than the standard read sequence

Modulation-Specific Status:

2.3 FIFO Access
2.3.1 Direct Write Command
In the LR2021, direct write commands allow data to be written directly to the transmit FIFO buffer without requiring command
processing at the NSS rising edge. This optimized mechanism enables high-speed data transfer for transmission by writing data byteby-byte into the radio FIFO immediately after the opcode is parsed, significantly improving SPI operation efficiency.

2.3.2 Direct Read Command
The LR2021 has a special "direct read" command (ReadRadioRxFifo(...)) that operates differently from the standard read pattern.
As described in Section 5.4.1.3 of the Datasheet, this command returns data in the same SPI frame as the command, without requiring
a second SPI transaction. This speeds up data retrieval from the RX FIFO, making it more efficient to read received packets.

2.4 Monitoring FIFO Level
The LR2021 has two 256-byte data buffers (FIFOs) - one for transmission (TX FIFO) and one for reception (RX FIFO). Monitoring the fill
levels of these FIFOs is crucial for efficient data management, especially when working with large data packets. The LR2021 offers
three main methods for monitoring FIFO levels, each with its own advantages.

2.4.1 IRQ-Based FIFO Monitoring
The LR2021 can generate interrupts based on the FIFO fill levels, which allows an efficient and event-driven approach, reducing CPU
overhead by only processing when needed. This is configured using the ConfigFifoIrq(...) command.
The available FIFO Flags are as follows:

o

0x01: FifoEmpty – FIFO is empty

o

0x02: FifoLow - FIFO level is below the low threshold

o

0x04: FifoHigh - FIFO level exceeds the high threshold

o

0x08: FifoFull - FIFO is full

o

0x10: FifoOverflow - FIFO has overflowed

o

0x20: FifoUnderflow - FIFO has underflowed

It is also necessary to map the IRQs to DIO Pins, calling the command SetDioIrqConfig(DioPin, IRQ_RX_FIFO | IRQ_TX_FIFO).
The host controller can monitor the DIO pin state, receiving an interrupt when the configured FIFO condition occurs.
The host can then check which specific FIFO flag triggered the interrupt using command GetFifoIrqFlags(...)
For example, to receive large packets (>256 bytes), configure RX FIFO to trigger an IRQ when it is nearly full (e.g., at 200 bytes). When
the IRQ triggers, read from the RX FIFO while continuing to receive data, preventing overflow.

2.4.2 Status Flag-Based FIFO Monitoring
Beyond IRQs, the LR2021 can directly map FIFO status flags to DIO pins, providing real-time status indication, using the command
SetDioFunction(DioPin, DIO_FUNCTION_FIFO_STATUS).
The specific status flag (empty, full, level threshold) is then mapped to the DIO pin. The DIO pin directly reflects the status of the
selected FIFO condition, changing state immediately when the condition changes.
For example, map a "TX FIFO empty" flag to a DIO pin. After detecting the pin has gone high (indicating the FIFO is empty), the host
knows it can immediately write a new batch of data without having to poll the device.

2.4.3 API-Based FIFO Level Monitoring
For more detailed control or when precise FIFO level information is needed, the LR2021 provides API commands to directly read the
current FIFO levels.
•
•

GetRxFifoLevel(...) returns the exact number of bytes currently in the RX FIFO. Similarly,
GetTxFifoLevel(...) returns the exact number of bytes currently in the TX FIFO.

The host MCU can periodically poll these commands to get precise FIFO fill levels.
When implementing a flow control mechanism, periodically check GetTxFifoLevel(...) to determine how much more data can be
written before filling the TX FIFO.

2.4.4 Practical Implementation Strategy
For optimal FIFO management, especially for large data transfers, a combined approach often works best:
For TX operations:

1.

Configure TX FIFO low threshold IRQ to trigger when the FIFO has space for new data.

2.

When the IRQ triggers, check GetTxFifoLevel(...) to determine exactly how much space is available.

3.

Write new data to the FIFO using WriteRadioTxFifo(...).

For RX Operations:
1.

Configure RX FIFO high threshold IRQ to trigger when the FIFO is nearly full.

2.

When the IRQ triggers, check GetRxFifoLevel(...) to determine how many bytes to read.

3.

Read data from the FIFO using ReadRadioRxFifo(...).

4.

For continuous reception, clear the RX IRQ flag using ClearFifoIrqFlags(...).

3 General Configuration Steps
For both transmission and reception, the following general steps apply regardless of the modulation used:
1.

Configure general parameters: Set RF frequency, PA configuration, and DIO functions.

2.

Select the specific packet type: Use SetPacketType(...) to define the modulation to be used.

3.

Configure the modulation-specific parameters: Set modulation and packet parameters for the selected packet type.

4.

Trigger the transmission or the reception:

o

For transmission: Load data to transmit FIFO and initiate TX.

o

For reception: Configure reception parameters and start RX.

Note that modulation-specific commands are available for packet type and modulation parameters of the supported modulations.
The following steps are similar across all modulation types:

1.

Set standby mode as default state to start the transmission of reception of the radio packets.

2.

Select RF frequency.

3.

Configure PA (Power Amplifier).

4.

Set TX power and ramp time.

5.

Write data to TX FIFO and start transmission, or start reception and then read received data from RX FIFO.

Note: SelPA (…) command allows to switch between PAs, without wanting to re-configure the parameters of the Pas. It has then
to be called after the SetPaConfig (…) command

o

o

header_type: 0 for explicit, 1 for implicit

4.3 LoRa® Packet Reception
The following steps are necessary to allow a LoRa® Packet reception:
1.

Set Standby mode: for example SetStandby(0x01) // StandbyXOSC mode.

2.

Set packet type to LoRa®: SetPacketType(0x00) // LoRa® (default).

3.

Configure RF frequency: SetRfFrequency(frequency_in_Hz) // e.g., 915000000 for 915MHz.

4.

Configure RX path: SetRxPath(0x00, 0x00) // RxPath=0 for LF, RxBoost=0 for normal mode.

5.

Configure LoRa® modulation parameters: SetLoraModulationParams(SF, BW, CR, LDRO). Ensure that these
parameters match with the transmitter.

6.

Configure LoRa® packet parameters: SetLoraPacketParam(preamble_length, header_type, payload_length, CRC,
IQ_inversion). Match these parameters with the transmitter.

Note: when payload_length is set to 0: the device accepts any payload length (no length filtering). When set to 1-255: the device only
accepts payloads with lengths from 1 to the specified value. Payloads with length 0 or exceeding this value will be rejected, triggering
a header error interrupt (IRQ_HEADER_ERROR).
7.

Configure IRQ settings for reception: SetDioIrqConfig(dio_pin, IRQ_RX_DONE | IRQ_CRC_ERROR | IRQ_TIMEOUT).

8.

Start reception: SetRx(timeout) // timeout in 32kHz clock periods, 0xFFFFFF for continuous mode.

9.

Wait for reception by monitoring IRQ_RX_DONE.

10. Read received data: GetRxPktLength(...) // Get received packet length.
11. ReadRadioRxFifo(buffer, length) // Read data from RX FIFO.
12. Check packet status: GetLoraPacketStatus(...) // Get RSSI, SNR, and error information.
You can also configure multi-SF detection (to allow detection of multiple spreading factors simultaneously) using commands:
•
•

SetLoraSideDetConfig(Config1, Config2, Config3) and
SetLoraSideDetSyncword(Syncword1, Syncword2, Syncword3).

6 Sending/Receiving Long GFSK Packets
This section describes the necessary operations to transmit GFSK payloads larger than 256 bytes.
The transceiver can send payloads larger than the internal FIFO. Since this FIFO is only 256 bytes, it will need to be written to
multiple times while transmitting to send long payloads.
Every time a byte is transmitted, it is removed from the FIFO. Sending large payloads requires that the TX FIFO is refilled whenever it
gets under a certain threshold of data.
When receiving large payloads, you need to keep reading from the FIFO when it is filled above a certain threshold.
The FIFO is accessible while receiving and transmitting.

same data rate. This section describes the steps to send or receive an FLRC radio packet.

11 DIO RX/TX Trigger
Packet transmission and reception can be triggered using DIO pins, in addition to SPI commands.
Using DIO pins to trigger TX/RX operations offers significant advantages over SPI command-based triggering:
•

Reduced Latency: Eliminates SPI bus transaction time and internal command parsing overhead, enabling faster response to
triggering events.
Precise Timing Control: Allows the host MCU to trigger transmissions or receptions at precise moments using hardware timers
or other GPIO-driven mechanisms. This is particularly valuable for time-synchronized networks, scheduled transmissions, or
applications requiring deterministic timing that cannot be achieved through software-based SPI command sequences.
Lower Host CPU Overhead: The host can configure the trigger once and use simple GPIO toggling rather than constructing and
transmitting full SPI command sequences.

•

•

The necessary steps are the following:

•

Configure the DIO(s) to be used as TX and/or RX triggers

•

Set the default RX/TX timeout to be used when triggering RX or TX

•

Set the configured DIOs as logical HIGH to trigger RX or TX

•

Reset the pin to LOW once the operation is completed, or after the minimum HIGH time

The following example shows how to configure a DIO to act as a TX trigger (this example is based on the LR2021 C driver and uses DIO
number 8):
lr20xx_system_dio_t

dio = LR20XX_SYSTEM_DIO_8;

lr20xx_system_dio_func_t

dio_function = LR20XX_SYSTEM_DIO_FUNC_TX_TRIGGER;

lr20xx_system_dio_drive_t dio_drive = LR20XX_SYSTEM_DIO_DRIVE_NONE;
lr20xx_system_set_dio_function( context, dio, dio_function, dio_drive );
